# Работа с проектом

## Контекст

Активный кейс с 15 ноября 2026: «ИИ Агент поиска ответов на вопросы по
корп.документам», трек «Корпоративные процессы». Описание проблемы, FAQ
и обращение заказчика получены. Подробное ТЗ и файлы ожидаются на кик-оффе.
Прежний эксперимент поддержки находится в archive/support-agent/ и не задаёт
архитектуру нового кейса.

Начать с README.md, docs/product/BRIEF.md, docs/preparation/HACKATHON.md
и docs/preparation/AUDIT.md. Перед конкурсной разработкой сверить этап и
актуальный регламент. Не выдавать подготовительные каталоги за работающий
прототип. Не скрывать происхождение архивных наработок.

## Стек и реализация

- React + Vite + TypeScript; Python 3.12 + FastAPI; SQLite + FTS5;
  ChromaDB; PyMuPDF; python-docx; Docker Compose.
- Контур разработки и демонстрации описан в docs/preparation/ORGANIZER_QA.md.
  Приложение использует локальные chat и embeddings через раздельные адаптеры.
  Совместимость API проверять на конкретной сборке и модели.
- Реализовать первым импорт файлов, FTS5 и ответ с проверяемыми цитатами
  по нескольким документам. Затем подключить локальные embeddings и Chroma.
  ACL/SSO, UI загрузки и дополнительную аналитику брать после основного сценария.
- Предусмотреть явную отправку примера применения выбранного пункта.
  Сохранять его с привязкой к существующей цитате и версии источника.
  До проверки человеком запись недоступна из поиска по регламентам.
  При показе проверенных записей именовать их практикой и держать отдельно
  от нормативных оснований.
- Один backend и ограниченный агентский цикл; несколько агентов и брокер
  задач добавлять только при подтверждённой необходимости.
- SQLite — источник истины для документов, версий, разрешений, фрагментов,
  заданий и истории. Chroma — перестраиваемый индекс, не источник прав доступа.
- Исходный текст и его координаты сохранять до chunking. Цитата содержит
  document_version_id, block/chunk ID и точный locator. DOCX не имеет
  стабильных номеров страниц без отдельного процесса рендеринга.
- Не смешивать embeddings разных профилей/размерностей. Смена профиля требует
  новой генерации индекса; переключение после полной проверки готовности.
- Не определять действующую редакцию по времени загрузки или имени файла.
  Не назначать универсальное старшинство приказов, писем и регламентов.
- До поиска/выдачи и перед возвратом ответа проверять доступ к источникам.
  user_id/groups из тела запроса и инструкция внутри документа не дают прав.
- Агентские инструменты только читают разрешённый корпус. Загрузка/публикация
  редакции/удаление — отдельные административные операции.
- Отделять подтверждённые сведения от конфликтов и пробелов. При недостатке
  доказательств уточнять вопрос или сообщать, что ответ не найден.
- Валидировать структуру ответа, существование и доступность всех ссылок.
  Корректный ID цитаты сам по себе не доказывает, что источник поддерживает вывод.
- Исключать ключи и полные тексты документов/вопросов из обычных логов.
  Корпус, embeddings, вопросы и ответы остаются в контуре команды.
- Сценарии качества описаны в docs/quality/EVALUATION.md. Разделять проверки
  без модели, live LLM и live embeddings; не заявлять непройденные проверки.
- Для сдачи подготовить доступный жюри URL стенда с локальным контуром
  и расчёт стоимости одного запроса. Требования и сроки в docs/preparation/HACKATHON.md.
- Не применять требования старого кейса о возвратах/скидках/одобрении писем
  к новому read-only вопросно-ответному процессу.

## Среда

Windows / PowerShell. Для текущих подготовительных проверок использовать
.venv/Scripts/python.exe; существующая среда относится к старому кейсу и
не доказывает готовность нового стека. Не менять глобальный Python.
Node/npm и Docker CLI доступны; состояние Docker Engine проверять отдельно.
Секреты — в .env; runtime и входные корпоративные файлы не включать в Git.
Фиксировать версии backend/frontend и образы перед проверяемой сборкой.
Документация и сообщения пользователю — на русском; код и API — на английском.
