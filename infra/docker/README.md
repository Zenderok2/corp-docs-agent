# Проект Docker Compose

Сейчас здесь спецификация. Исполняемые `compose.yaml`, Dockerfile и конфигурация
reverse proxy ещё не созданы. Docker CLI установлен; Engine при проверке
15 ноября недоступен. Реальная контейнерная сборка не проверялась.

| Сервис | Назначение | Доступ/хранение |
| --- | --- | --- |
| frontend | Сборка Vite, раздача статики, прокси /api к backend | Локальный 8080 для проверки. На стенде через единый HTTPS-вход |
| backend | FastAPI, runner ingestion и агентский процесс | Только внутренняя сеть; app_data для SQLite, оригиналов и извлечённых блоков |
| chroma | Сервер индекса | Только внутренняя сеть; отдельный chroma_data |
| llm-chat | Локальный llama.cpp для генерации | Только внутренняя сеть; веса команды в отдельном read-only mount |
| llm-embed | Локальный llama.cpp для embeddings в hybrid-профиле | Только внутренняя сеть; веса отдельно |

Первый проход на Windows запускается нативно с FTS5 и локальным chat endpoint.
В Compose адреса chat и embeddings задаются по именам сервисов. Подготовить
образы, веса и зависимости до отключения внешнего доступа. Изоляцию и отсутствие
исходящих запросов проверить на выбранном хосте вместе с доступом к UI.

Для разработки вне контейнеров можно явно опубликовать backend на 127.0.0.1:8000,
Chroma на 127.0.0.1:8001, Vite на 127.0.0.1:5173. Внутри Compose backend
подключается к `chroma:8000`, а не к localhost. Vite dev server — только режим разработки.

SQLite не требует отдельного контейнера. Chroma не должна использовать файл
app.sqlite3 или общий каталог приложения. Пути хранения Chroma и healthcheck
сверить с документацией выбранного зафиксированного образа; не копировать
случайные переменные окружения разных версий.

В спринте подготовить:

- Multi-stage frontend build, backend без dev dependencies и запуска от root.
- Фиксированные версии зависимостей и образов; `latest` не использовать в проверяемой сборке.
- Healthchecks, ожидание готовности, повтор соединения и startup диагностику.
- Ограничение ресурсов на обработку загружаемых файлов и один ingestion worker.
- Compose volumes отдельно от fixtures, env_file с локальными секретами,
  frontend без доступа к этим секретам.
- Проверку fresh start → upload → ask → restart → repeat; без потери версий и ссылок.
- План backup SQLite/оригиналов и воспроизводимого перестроения Chroma.

Не удалять тома при обычном перезапуске; reset — отдельная явно обозначенная
операция только для тестовых данных. Не считать `depends_on` гарантией
готовности зависимого сервиса без health/retry-проверки.

## Контур конкурсного стенда

Для сдачи нужен работающий URL. Для самого агента и живого показа нужен
изолированный контур с самостоятельно размещёнными моделями. Согласовать
с организатором доступ жюри и допустимый демо-корпус. Условия в
[правилах сдачи](../../docs/preparation/HACKATHON.md).

1. Выбрать хост команды с постоянным подключением и ресурсом для локальной
   модели. Для одного проверенного пользователя достаточно нативного
   запуска с FTS5. Compose нужен, если он упрощает восстановление.
2. Вывести через HTTPS только интерфейс и API, нужные жюри для сценария.
   Модели, Chroma, SQLite, папка корпуса и очередь проверки остаются внутри.
   На стенде доступны только согласованные материалы. Для живого ввода
   использовать лимиты запросов, времени и размера данных.
3. Проверить URL с другого устройства по согласованной схеме входа и пройти
   составной вопрос, открыть источник и выполнить сценарий сбора практики.
   Шаги команды качества показать из служебного доступа.
4. Проверить повторный старт, модельные веса и восстановление базы заметок.
   Записать SHA сборки, ответственного за доступность и команду перезапуска.
   Сохранить версии моделей и базы для повторного показа.
